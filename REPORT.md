## 1. Описание AI-инструмента

**Инструмент**: [OpenCode](https://opencode.ai/docs/) — open-source AI-агент-харнесс (CLI/TUI, клиент-серверная архитектура), работает с разными LLM-провайдерами. Выбран потому, что вся работа по ДЗ ведётся в нём: инструкции можно проверить на живом агенте в чистой сессии без дополнительных инструментов.

**Официальный механизм подключения инструкций** (по документации [Instructions](https://opencode.ai/docs/instructions/)):

- формат — файл **`AGENTS.md`**. OpenCode V2 распознаёт **только** `AGENTS.md`; `CLAUDE.md` как fallback **не используется**;
- `AGENTS.md` кладётся в каталог, к которому относится руководство. Загружаются: глобальный `~/.config/opencode/AGENTS.md` + все `AGENTS.md` от рабочего каталога вверх до домашней директории (для каталогов вне home — до корня проекта). Файлы **объединяются**, конфликты не разрешаются — их просто нет в модели «override»;
- вложенные `AGENTS.md` подгружаются по мере исследования проекта агентом (при чтении файла/каталога);
- **приоритизация/порядок сборки контекста**: system prompt агента/провайдера → инструкции Code Mode → guidance MCP-серверов, references и скиллов → глобальный и проектные `AGENTS.md` + файлы из конфига `instructions` → дата и окружение → сессионные инструкции из API;
- дополнительно можно подключить файлы/глобы/URL через массив `instructions` в `opencode.json(c)` — они грузятся **после** `AGENTS.md`;
- файлы инструкций **коммитятся в репозиторий**, чтобы инженеры и агенты работали в одних границах;
- правки в `AGENTS.md` подхватываются «на лету» перед следующим запросом; правки во **вложенных** файлах не детектируются автоматически — нужна новая сессия (важно для процедуры проверки: после правок инструкций проверку запускаем в новой сессии).

**Практический вывод для ДЗ**: создаём `AGENTS.md` в корне форка (правила уровня всего репозитория) — это единственный официально поддерживаемый путь, агент подхватывает файл автоматически при старте сессии в проекте.

#### Неудачная попытка №1: тесты падают «сами по себе»

Первый же запуск `./gradlew test` в чистом клоне (до каких-либо изменений) дал массовые падения:

```
org.mockito.exceptions.base.MockitoException: Mockito cannot mock this class: class android.view.ViewGroup.
Underlying exception: Could not modify all classes [interface android.view.KeyEvent$Callback, class java.lang.Object, ...]
Java: 17
```

Падали только тесты, создающие моки через `Mockito.mock(...)` (например, `AbsDelegationAdapterTest.java:81`, `LayoutContainerListAdapterDelegateDslTest.kt:18`), а тесты с рукописным `SpyableAdapterDelegate` проходили. Всего: 8 упавших тестовых тасков (debug/release × 4 модуля).

**Разбор.** Первая мысль — «сломан проект/наш форк». Опровергается: дерево чистое, изменений нет. Дальше — анализ stack trace из `build/test-results/` и состава зависимостей:

- в `build.gradle` зафиксирован `org.mockito:mockito-inline:2.21.0` (2018 г., внутри Byte Buddy 1.8.x);
- юнит-тесты Android-модулей выполняются на том же JVM, что и Gradle, а по умолчанию на машине — JDK 17;
- inline-mock-maker старого Byte Buddy не умеет инструментировать классы на JDK 17 — отсюда «Mockito cannot mock this class»;
- в `.github/workflows/` проекта CI гоняет сборку на **JDK 11** — там всё зелёное.

**Проверка гипотезы** — прогон тех же тестов под JDK 11:

```bash
JAVA_HOME=/Users/igorsergeev/Library/Java/JavaVirtualMachines/jbr_dcevm-11.0.16/Contents/Home \
  ./gradlew :library:testDebugUnitTest :kotlin-dsl:testDebugUnitTest
# → BUILD SUCCESSFUL
```

**Вывод и решение.** Падения — не баг кода, а несовместимость старого тулчейна проекта (mockito-inline 2.21 + Gradle 7.0.2 + AGP 7.0.3) с JDK 17. Решение: гонять тесты под JDK 11 (как CI), путь к JDK фиксируется в инструкциях для AI («тесты требуют JDK 11»), апгрейд Mockito отклонён как отклонение от апстрима. Этот случай отдельно лёг в план инструкций: агент обязан знать про JDK 11 и про «известные падения».

_Урок для будущего `AGENTS.md`: без явного указания «запускай тесты под JDK 11» любой агент (и любой инженер) потратит время на ту же ложную трассу._

Находки анализа, повлиявшие на содержание:

- `app/` (сэмпл с `ReptilesActivity`, `DiffActivity`, `PaginationActivity`) **исключён из `settings.gradle`** коммитом `exclude :app` — то есть не собирается `./gradlew build`. В инструкциях это зафиксировано явно, иначе агент будет пытаться его собирать/чинить;
- зависимость модулей однонаправленная (`kotlin-dsl*`, `paging` → `library`) — зафиксирована как граница;
- Java/Kotlin-разделение не случайно: `library` и `paging` на Java публикуются для Java-потребителей — зафиксирован запрет «переписывать на Kotlin»;
- опыт «Неудачной попытки №1» (JDK 11 vs 17) сразу внесён в блок «Как запустить и проверить» — чтобы агент (и инженер) не наступили на те же грабли.

#### Доработка черновика по ревью

**Промпт 6 (к агенту):**
> в agents.md не хватает
> 1) перечиление стека технологий
> 2) перечисление карты модулей и зачем нужен каждый
> 3) правил безопасности для агента, например, не хардкодить секреты и тому подобное
> 4) инструкция, что делать, если не нашел информацию в agents.md - если не нашел информацию, то не додумывай, а изучи отрезок кода

Первый черновик оказался неполным: агент описал назначение модулей таблицей «ответственность», но не дал карту репозитория «зачем нужен каждый каталог», не перечислил стек технологий и не предусмотрел блоки про безопасность и поведение при отсутствии информации. Это ожидаемая проблема «инструкции пишет сама модель»: модель ужимает контекст до существенного, а для инструкций критична полнота.

Что добавлено по каждому пункту (факты брались из build-файлов и конфигов, не из памяти):

1. **Стек технологий** — таблица с версиями (Java 8 / Kotlin 1.5.31, Android SDK 31/min 14, RecyclerView 1.2.1, Paging 2.0.0, JUnit 4.12, mockito-inline 2.21.0, Gradle 7.0.2 / AGP 7.0.3, maven-publish 0.18.0) + запрет на «модернизацию» стека по своей инициативе.
2. **Карта репозитория** — дерево каталогов с аннотацией, зачем каждый нужен (включая `gradle.properties` как источник версий и `app/` вне сборки).
3. **Правила безопасности** — 6 правил: не хардкодить секреты (env-переменные как в CI), не коммитить/не светить `local.properties` и credentials, не ослаблять `.gitignore`, никаких деструктивных git-действий и публикаций без подтверждения, не подключать внешние сервисы, не отключать проверки ради зелёной сборки.
4. **«Если информации нет»** — не додумывать, изучать код и его тесты; порядок источников истины (код/тесты → README → build-файлы → git history); ссылаться на файлы и строки в ответах; неоднозначность — выносить вопросом пользователю.

_Вывод из этой итерации: генерацию инструкций моделью обязательно надо проводить с ручным чек-листом полноты (контекст / стек / карта / границы / безопасность / «что если нет информации») — сама модель эти блоки не «досочиняет»._
